> 核心觀點首發於 [X](https://x.com/realchendahuang/status/2087949416808518106)，這篇文章是完整版論述。

現在一堆 AI Coding Agent 動不動就上 TUI，這股風氣，Claude Code 得負很大責任。它把「在終端裡跟 AI 對話寫代碼」這件事做得很極致，但也把一條審美和路徑依賴帶了起來：好像真正高級的 Coding Agent，就得默認是終端介面；Web 端反而是附屬，甚至被嘲成「不夠程式設計師」。

結果呢？先搞一個複雜的 TUI，各種顏色、狀態列、快捷鍵、模式切換，然後美其名曰「沉浸式」「高效」「尊重程式設計師」。

真的嗎？

## 你以為在對話，其實在搏鬥

對一小部分每天泡在終端的人來說，TUI 確實爽。但對更多人來說，它是在人為製造門檻。用 TUI 跟 Agent 協作時，你其實在不斷做三件事：

**回憶快捷鍵和模式。**每個工具都有一套自己的鍵位習慣，新用戶一臉懵，老用戶換工具也得重新適應。

**在滾動的字符流裡定位信息。**狀態不是攤開給你看的，而是埋在時間軸裡的，你得靠滾動和搜索去「考古」。

**祈禱自己沒有誤觸進入某個奇怪狀態。**模式切換是隱形的，你經常不知道自己當前處於哪個模式，直到出了問題。

這已經不是互動了，這是在跟介面搏鬥。

## 信息密度不等於信息效率

TUI 的辯護者最愛說的一個詞是「信息密度」。但信息密度堆到極致，代價是可讀性和可恢復性被踩到最低。

真正高效的介面，應該是**把狀態攤開給你看**，讓你用眼睛和空間感去理解——哪個任務在跑、哪條會話在等輸入、哪個文件被改了，一眼掃過去就知道。而不是逼你把所有東西都塞進短期記憶裡，用腦子維護一張「當前系統狀態」的隱形地圖。

人的工作記憶只有四到七個槽位。TUI 的互動模型，本質上是把最寶貴的認知資源花在「記住介面狀態」上，而不是「思考問題」上。

## 它還在培養一種壞習慣

更糟的是，TUI 生態在培養一種很壞的價值判斷：**把會不會用某個工具的鍵位當成能力本身。**

結果就是，人花大量精力在適應介面，而不是在思考問題。衡量一個程式設計師的標準，變成了「能不能背誦這套快捷鍵」，而不是「能不能把問題拆解清楚」。

一個好的工具應該降低思考成本，而不是把思考成本轉移到「如何操作這個介面」上。

## Web UI 完全可以又快又乾淨

有人說 Web 端慢、不夠「原生」。2026 年了，這個論點早就站不住了。

Web UI 完全可以做得又快又乾淨：裝成 PWA 之後跟桌面客戶端幾乎沒有區別，更新還更方便——不用用戶手動升級，刷新一下就是最新版。長會話、多任務並行、任務狀態可視化，這些恰恰是瀏覽器 DOM 的強項，而不是字符流的強項。

我自己的主力配置就是 OpenChamber 這種 Web 介面 + OpenCode 內核，長期高強度使用，穩得很。真要認真挑刺的話，Web 端偶爾的小毛病遠不影響長期使用，倒是某些 TUI 的模式切換坑過我很多次。

## 工具是給人用的，不是用來證明誰更「極客」的

Claude Code 本身很強，這點沒問題。但它把「TUI 才是正統」這個審美和路徑依賴帶起來了，後面一堆跟風的就更離譜——連互動設計都懶得做，直接把「長在終端裡」當成高級的證明。

把反人類的互動包裝成高級，真是很滑稽的一件事情。

工具是給人用的。判斷標準應該永遠是：**它有沒有降低你完成任務的總成本？**如果一套介面讓你把精力花在「跟介面搏鬥」上，那它再「極客」也是負資產。

下次選 Coding Agent 的時候，把這個濾鏡摘了再選。
