> 核心观点首发于 [X](https://x.com/realchendahuang/status/2087949416808518106)，这篇文章是完整版论述。

现在一堆 AI Coding Agent 动不动就上 TUI，这股风气，Claude Code 得负很大责任。它把「在终端里跟 AI 对话写代码」这件事做得很极致，但也把一条审美和路径依赖带了起来：好像真正高级的 Coding Agent，就得默认是终端界面；Web 端反而是附属，甚至被嘲成「不够程序员」。

结果呢？先搞一个复杂的 TUI，各种颜色、状态栏、快捷键、模式切换，然后美其名曰「沉浸式」「高效」「尊重程序员」。

真的吗？

## 你以为在对话，其实在搏斗

对一小部分每天泡在终端的人来说，TUI 确实爽。但对更多人来说，它是在人为制造门槛。用 TUI 跟 Agent 协作时，你其实在不断做三件事：

**回忆快捷键和模式。** 每个工具都有一套自己的键位习惯，新用户一脸懵，老用户换工具也得重新适应。

**在滚动的字符流里定位信息。** 状态不是摊开给你看的，而是埋在时间轴里的，你得靠滚动和搜索去「考古」。

**祈祷自己没有误触进入某个奇怪状态。** 模式切换是隐形的，你经常不知道自己当前处于哪个模式，直到出了问题。

这已经不是交互了，这是在跟界面搏斗。

## 信息密度不等于信息效率

TUI 的辩护者最爱说的一个词是「信息密度」。但信息密度堆到极致，代价是可读性和可恢复性被踩到最低。

真正高效的界面，应该是**把状态摊开给你看**，让你用眼睛和空间感去理解——哪个任务在跑、哪条会话在等输入、哪个文件被改了，一眼扫过去就知道。而不是逼你把所有东西都塞进短期记忆里，用脑子维护一张「当前系统状态」的隐形地图。

人的工作记忆只有四到七个槽位。TUI 的交互模型，本质上是把最宝贵的认知资源花在「记住界面状态」上，而不是「思考问题」上。

## 它还在培养一种坏习惯

更糟的是，TUI 生态在培养一种很坏的价值判断：**把会不会用某个工具的键位当成能力本身。**

结果就是，人花大量精力在适应界面，而不是在思考问题。衡量一个程序员的标准，变成了「能不能背诵这套快捷键」，而不是「能不能把问题拆解清楚」。

一个好的工具应该降低思考成本，而不是把思考成本转移到「如何操作这个界面」上。

## Web UI 完全可以又快又干净

有人说 Web 端慢、不够「原生」。2026 年了，这个论点早就站不住了。

Web UI 完全可以做得又快又干净：装成 PWA 之后跟桌面客户端几乎没有区别，更新还更方便——不用用户手动升级，刷新一下就是最新版。长会话、多任务并行、任务状态可视化，这些恰恰是浏览器 DOM 的强项，而不是字符流的强项。

我自己的主力配置就是 OpenChamber 这种 Web 界面 + OpenCode 内核，长期高强度使用，稳得很。真要认真挑刺的话，Web 端偶尔的小毛病远不影响长期使用，倒是某些 TUI 的模式切换坑过我很多次。

## 工具是给人用的，不是用来证明谁更「极客」的

Claude Code 本身很强，这点没问题。但它把「TUI 才是正统」这个审美和路径依赖带起来了，后面一堆跟风的就更离谱——连交互设计都懒得做，直接把「长在终端里」当成高级的证明。

把反人类的交互包装成高级，真是很滑稽的一件事情。

工具是给人用的。判断标准应该永远是：**它有没有降低你完成任务的总成本？**如果一套界面让你把精力花在「跟界面搏斗」上，那它再「极客」也是负资产。

下次选 Coding Agent 的时候，把这个滤镜摘了再选。
